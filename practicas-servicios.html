Azure para redes y servidores.

Estas prácticas muestran cómo guardar y compartir archivos, controlar puertos, diagnosticar una conexión, unir redes, repartir visitas entre servidores, vigilar una máquina y recuperar un disco. Cada laboratorio empieza desde cero y termina eliminando sus propios recursos.

Blob Storage y un enlace temporal

Crea una infografía o PDF, guárdalo de forma privada y compártelo con permisos limitados.

DIFICULTADBásica
COSTOMuy bajo
GRUPOrg-lab-blob

Piensa en un edificio de casilleros

La cuenta de almacenamiento es el edificio, el contenedor es un casillero y cada blob es un archivo. Un contenedor privado permanece cerrado hasta que alguien autorizado abre un archivo.

¿Qué problema resuelve?

Guarda imágenes, PDF, videos, instaladores o respaldos sin depender del disco de una VM. El archivo continúa disponible aunque no exista un servidor encendido.

FASE A · CREAR UN ARCHIVO CON SENTIDO

Diseña una evidencia útil para la clase

  1. Abre PowerPoint, LibreOffice Impress, Canva u otra herramienta disponible. No necesitas programar.
  2. Elige un tema: “Diferencia entre IP pública e IP privada”, “Cinco reglas para proteger una cuenta en la nube” o “Cómo evitar consumo innecesario en Azure”.
  3. Crea una página con título, tu nombre, tres ideas explicadas con tus palabras y un dibujo o diagrama sencillo. No copies contraseñas, claves ni datos personales.
  4. Exporta dos versiones: infografia-apellido.pdf y infografia-apellido.png. Si tu aplicación no exporta PNG, una captura recortada es suficiente.
  5. Abre ambos archivos en Windows. Comprueba que se leen y anota cuál ocupa más espacio.
✓

¿Por qué dos formatos?

El PDF conserva la presentación para lectura o impresión. El PNG es una imagen que suele mostrarse directamente en una página. Azure puede guardar ambos, aunque su tipo de contenido y tamaño sean distintos.

FASE C · CREAR EL CONTENEDOR Y CARGAR

Deja el casillero cerrado

  1. Dentro de la cuenta, usa el buscador del menú izquierdo y escribe Contenedores. También puedes bajar hasta Almacenamiento de datos → Contenedores.
  2. Selecciona + Contenedor. Nombre: evidencias.
  3. En Nivel de acceso anónimo, conserva Privado (sin acceso anónimo) y pulsa Crear.
  4. Abre evidencias, selecciona Cargar, busca los archivos PDF y PNG y confirma con Cargar.
  5. Abre cada blob y compara Tamaño y Tipo de contenido. El PDF normalmente aparece como application/pdf y el PNG como image/png.
  6. Copia la URL normal de uno de los blobs y pruébala en una ventana privada. Debe responder que no tienes autorización. Ese resultado confirma que el contenedor es privado.
No aparece “Contenedores” en el menú

Confirma que abriste una cuenta de almacenamiento, no un disco, una máquina virtual o el grupo de recursos. En el menú del recurso escribe contenedores en Buscar. Otra ruta posible es Explorador de almacenamiento → Contenedores de blobs. Si la cuenta aún se está implementando, actualiza el portal.

FASE D · COMPARTIR SOLO LO NECESARIO

Genera una llave que vence

  1. Abre el blob PDF y selecciona Generar SAS.
  2. En Permisos, marca únicamente Lectura. No marques escribir ni eliminar.
  3. Define una hora de inicio cercana y un vencimiento corto que alcance para la comprobación. Verifica que la zona horaria mostrada sea correcta.
  4. En Protocolos permitidos, elige Solo HTTPS. HTTPS cifra el viaje de los datos entre el navegador y Azure.
  5. Selecciona Generar token y dirección URL de SAS. Copia la URL de SAS de blob y ábrela en una ventana privada.
  6. Comprueba que el PDF abre con SAS y que la URL normal continúa bloqueada.
🔐

Una URL SAS es una credencial

Todo lo que aparece después del signo ? autoriza el acceso. No la publiques en una captura ni la envíes a personas ajenas. Cuando vence deja de funcionar, pero mientras esté activa debe protegerse.

Evidencias de la práctica

Limpieza obligatoria

  1. Guarda capturas sin mostrar el token SAS.
  2. Abre Grupos de recursos → rg-lab-blob → Eliminar grupo de recursos.
  3. Escribe el nombre solicitado, confirma y espera a que la eliminación termine.
  4. Busca el nombre de la cuenta en Todos los recursos; no debe aparecer.

02

Azure Files: una carpeta compartida

Organiza documentos en carpetas de nube y, si la red lo permite, móntalos como una unidad de Windows.

DIFICULTADBásica
COSTOBajo
GRUPOrg-lab-files

Piensa en la carpeta común de una oficina

Varios equipos pueden ver la misma estructura de carpetas. No hay que enviarse una copia diferente por correo cada vez que cambia un documento.

Blob no es igual a Files

Blob Storage guarda objetos y se usa mucho desde sitios y aplicaciones. Azure Files presenta carpetas y archivos mediante protocolos conocidos por los sistemas operativos, como SMB.

WindowsUnidad Z:

⇄

FASE A · PREPARAR MATERIAL

Crea un pequeño paquete de trabajo

  1. En Windows crea una carpeta llamada material-redes-apellido.
  2. Guarda dentro una infografía o PDF sobre topologías de red y una imagen creada por ti. Puedes reutilizar únicamente los archivos locales de la práctica anterior; no necesitas conservar ningún recurso de Azure.
  3. Crea dos subcarpetas: documentos e imagenes, y ordena los archivos.
  4. Comprueba que ningún archivo contenga datos privados o credenciales.
FASE B · CREAR EL RECURSO COMPARTIDO

Configura Azure Files clásico dentro de una cuenta

  1. Busca Cuentas de almacenamiento → + Crear.
  2. Suscripción: Azure for Students; grupo nuevo: rg-lab-files.
  3. Nombre único: stfilesapellido1234; rendimiento Estándar; redundancia LRS.
  4. Conserva los demás valores predeterminados, selecciona Revisar y crear → Crear → Ir al recurso.
  5. En el menú izquierdo abre Almacenamiento de datos → Recursos compartidos de archivos.
  6. Selecciona + Recurso compartido de archivos. Nombre: material-clase.
  7. En el nivel elige Transacción optimizada. Es una opción estándar para usos generales.
  8. Si aparece Capacidad máxima o Cuota, escribe 5 GiB. Es un límite de crecimiento; en almacenamiento estándar se cobra principalmente lo usado, no porque debas llenar los 5 GiB.
  9. Selecciona Crear y abre material-clase.
FASE C · CREAR CARPETAS Y CARGAR

Comprueba el comportamiento de un servidor de archivos

  1. Selecciona + Agregar directorio o Nuevo directorio y crea documentos.
  2. Crea también imagenes.
  3. Entra en cada directorio, selecciona Cargar y sube el archivo correspondiente.
  4. Descarga uno de los archivos con un nombre diferente. Ábrelo y verifica que el contenido no cambió.
  5. Copia la URL que muestra el portal y observa que no es una dirección pública para navegar libremente: el acceso exige autenticación.
Resultado esperado

El recurso compartido muestra dos carpetas, cada una conserva su archivo y puedes cargar o descargar desde el portal aun cuando el puerto 445 de la institución esté bloqueado.

FASE D · CONECTAR DESDE WINDOWS

Intenta mostrar Azure Files como una unidad de red

  1. Dentro del recurso compartido selecciona Conectar.
  2. Elige Windows y una letra, por ejemplo Z.
  3. Para una práctica guiada, selecciona el método con clave de la cuenta de almacenamiento. En un entorno real se prefiere autenticación basada en identidad porque facilita retirar permisos por usuario.
  4. Antes de ejecutar el script, abre PowerShell y prueba el puerto 445 reemplazando el nombre.
POWERSHELL · PROBAR SMB 
Test-NetConnection -ComputerName stfilesapellido1234.file.core.windows.net -Port 445
  1. Si TcpTestSucceeded muestra True, copia desde el portal el script de conexión y ejecútalo en PowerShell. Usa el script generado por tu cuenta; contiene la dirección y los datos correctos.
  2. Abre Explorador de archivos → Este equipo. Debe aparecer la unidad Z:.
  3. Crea dentro un directorio llamado prueba-windows y confirma en el portal que también aparece.
  4. Al finalizar ejecuta Remove-PSDrive -Name Z o desconecta la unidad desde el Explorador.
⚠

Si TcpTestSucceeded muestra False

La red institucional o el proveedor de Internet está bloqueando la salida TCP 445. No abras puertos en Azure y no desactives el firewall de Windows: eso no corrige un bloqueo externo. Completa la carga y descarga desde el portal y registra el resultado de la prueba como evidencia.

🔐

No compartas el script de conexión

Cuando usa la clave de la cuenta, el script contiene una credencial con mucho poder. No debe aparecer en capturas, PDF, chat ni correo. Cierra PowerShell y elimina la cuenta de almacenamiento al terminar.

Evidencias de la práctica

Limpieza obligatoria

  1. Desconecta la unidad Z: si llegó a montarse.
  2. Elimina rg-lab-files.
  3. Confirma en Todos los recursos que la cuenta stfiles... desapareció.

03

NSG y Network Watcher

Crea una VM temporal, descubre por qué HTTP está bloqueado y corrige únicamente la regla necesaria.

DIFICULTADBásica–media
COSTOConsume crédito mientras existe
GRUPOrg-lab-diagnostico

NSG es el portero del edificio

Cada regla indica quién puede entrar o salir, por qué puerta y con qué prioridad. Si ninguna regla permite una visita desde Internet, la regla final la rechaza.

Network Watcher es el investigador

Comprobación del flujo de IP simula un paquete TCP o UDP y muestra si Azure lo permite o lo niega, incluyendo el nombre de la regla responsable.

FASE B · INSTALAR NGINX SIN ABRIR SSH

Usa el canal de administración de Azure

  1. En la VM abre Operaciones → Ejecutar comando → RunShellScript.
  2. Pega y ejecuta el siguiente bloque.
UBUNTU · INSTALAR EL SERVICIO 
sudo apt-get update
sudo apt-get install -y nginx
echo '<h1>Servidor de diagnostico funcionando</h1>' | sudo tee /var/www/html/index.html
sudo systemctl enable --now nginx
sudo systemctl is-active nginx
curl -I http://localhost

RunShellScript llega mediante el agente de Azure instalado en la VM; por eso puede administrar el sistema aunque no hayas publicado SSH. curl localhost prueba NGINX desde dentro, pero todavía no demuestra acceso desde Internet.

Resultado esperado

La salida incluye active y una respuesta HTTP/1.1 200 OK. El navegador externo continúa sin abrir porque el NSG aún niega el puerto 80.

FASE C · ENCONTRAR LA REGLA QUE BLOQUEA

Simula una visita HTTP

  1. Busca Network Watcher en el portal.
  2. En Herramientas de diagnóstico de red, abre Comprobación del flujo de IP.
  3. Selecciona la suscripción, grupo, VM vm-diagnostico y su interfaz de red.
  4. Configura: protocolo TCP, dirección Entrada, dirección IP local privada de la VM, puerto local 80, IP remota 203.0.113.10 y puerto remoto 60000.
  5. Selecciona Comprobar flujo de IP.
  6. Anota el resultado y la regla. Debe indicar acceso denegado por una regla como DenyAllInBound.
ℹ

¿Qué representan esas direcciones?

La IP local es el destino dentro de Azure. La IP remota representa al visitante. 203.0.113.10 pertenece a un bloque reservado para documentación: la prueba estudia reglas y no envía una visita real desde esa dirección.

Corrige el control de acceso

  1. Regresa a la VM y abre Redes → Configuración de red.
  2. Selecciona Crear regla de puerto o abre el NSG asociado y entra en Reglas de seguridad de entrada → + Agregar.
  3. Configura los valores siguientes.

04

Emparejamiento de redes virtuales

Construye dos redes separadas y permite que sus servidores se comuniquen por direcciones privadas.

DIFICULTADMedia
COSTODos VM temporales
GRUPOrg-lab-peering

Dos barrios con una vía privada

Cada VNet es un barrio con su propia numeración. El emparejamiento construye una vía entre ambos usando la red troncal de Microsoft, no la Internet pública.

La regla que evita choques

Los rangos IP no pueden superponerse. Si dos redes usan las mismas direcciones, Azure no puede saber a cuál enviar el paquete.

Espacio de direccionesConjunto general de IP privadas de una VNet.
SubredParte más pequeña donde se conectan las interfaces.
PeeringRelación que permite enrutar entre dos VNet.
IP privadaDirección usada dentro de redes autorizadas, no desde Internet.
vm-a10.10.1.x
→
vnet-a10.10.0.0/16
⇄ peering
vnet-b10.20.0.0/16
→
vm-b10.20.1.x
FASE A · CREAR DOS REDES DIFERENTES

Define una numeración sin repetición

  1. Busca Redes virtuales → + Crear.
  2. Crea el grupo rg-lab-peering y la red vnet-a.
  3. En Direcciones IP, configura espacio 10.10.0.0/16 y subred subnet-a con 10.10.1.0/24. Selecciona Revisar y crear → Crear.
  4. Repite para vnet-b, en el mismo grupo y región, con espacio 10.20.0.0/16 y subred subnet-b 10.20.1.0/24.
  5. Dibuja los dos rangos. Observa que comienzan por 10.10 y 10.20; por eso no se pisan.
NotaciónLectura sencilla
/16Reserva una red amplia; contiene muchas direcciones para crear subredes.
/24Subred de 256 direcciones totales; Azure reserva algunas para su funcionamiento.
No superposiciónNinguna IP de 10.10.0.0/16 pertenece a 10.20.0.0/16.
FASE B · CREAR UNA VM NUEVA EN CADA RED

Usa IP pública solo para preparar y luego retírala

  1. Crea vm-a con Ubuntu Server LTS, tamaño pequeño y grupo rg-lab-peering.
  2. En Redes, selecciona vnet-a y subnet-a. Crea una IP pública estándar llamada pip-temporal-a, pero deja los puertos públicos en Ninguno.
  3. Crea vm-b de la misma forma, conectada a vnet-b y subnet-b, con la IP pip-temporal-b y sin puertos públicos.
  4. En Información general de cada VM anota su Dirección IP privada. No asumas que terminará en .4: copia el valor real.
  5. En vm-b abre Operaciones → Ejecutar comando → RunShellScript e instala NGINX con el bloque siguiente.
VM-B · SERVICIO DE PRUEBA 
sudo apt-get update
sudo apt-get install -y nginx
echo '<h1>Respuesta privada desde vm-b</h1>' | sudo tee /var/www/html/index.html
sudo systemctl enable --now nginx
curl -I http://localhost
  1. En vm-a ejecuta sudo apt-get update y sudo apt-get install -y curl.
  2. Abre la interfaz de red de cada VM: Redes → Configuración de red → nombre de la interfaz → Configuraciones IP → ipconfig1.
  3. Selecciona Desasociar en la IP pública y guarda. Después busca y elimina pip-temporal-a y pip-temporal-b.
  4. Confirma que ambas VM conservan su IP privada, pero ya no muestran dirección IP pública.
ℹ

¿Por qué la IP fue temporal?

Desde 2026, las subredes nuevas del portal son privadas de forma predeterminada. NGINX y curl se descargan desde Internet, así que necesitan una salida explícita. La IP pública estándar proporciona esa salida sin publicar puertos de entrada; después se retira para que la comunicación del ejercicio sea únicamente privada.

FASE C · COMPROBAR QUE TODAVÍA ESTÁN SEPARADAS

Haz una prueba antes de construir la conexión

  1. Abre vm-a → Operaciones → Ejecutar comando → RunShellScript.
  2. Reemplaza IP_PRIVADA_VM_B por el valor real y ejecuta:
VM-A · PRUEBA ANTES DEL PEERING 
curl --connect-timeout 5 -I http://IP_PRIVADA_VM_B

Debe agotarse el tiempo o indicar que no hay ruta. NGINX funciona, pero las dos VNet todavía no conocen un camino entre sí.

FASE D · CREAR EL EMPAREJAMIENTO

Construye la vía en ambos sentidos

  1. Abre vnet-a → Configuración → Emparejamientos.
  2. Selecciona + Agregar.
  3. En el vínculo local escribe vnet-a-a-vnet-b.
  4. En Red virtual remota, elige tu suscripción, vnet-b y escribe vnet-b-a-vnet-a para el vínculo remoto.
  5. Conserva activado Permitir que la red virtual acceda a la red virtual remota en ambos sentidos. No habilites uso de puerta de enlace ni tráfico reenviado: no se necesitan para esta prueba directa.
  6. Selecciona Agregar. El portal puede crear las dos direcciones desde el mismo formulario.
  7. Comprueba que ambos vínculos muestran estado Conectado. Si uno queda en Iniciado, falta crear o autorizar el sentido contrario.
ℹ

El emparejamiento no fusiona las redes

Cada VNet conserva sus direcciones, subredes y reglas. Peering solo agrega rutas privadas entre ellas. Los NSG siguen decidiendo qué puertos están permitidos.

FASE E · PROBAR LA VÍA PRIVADA

Repite la solicitud desde vm-a

  1. En el NSG de vm-b, revisa las reglas de entrada. La regla predeterminada AllowVnetInBound normalmente incluye redes emparejadas mediante la etiqueta VirtualNetwork.
  2. En vm-a, ejecuta otra vez curl -I http://IP_PRIVADA_VM_B.
  3. Debe aparecer HTTP/1.1 200 OK. Para ver el contenido usa curl http://IP_PRIVADA_VM_B.
  4. Explica por qué funcionó sin IP pública: el tráfico viajó por las direcciones privadas y el peering.
Resultado esperado

Peering aparece Conectado y vm-a recibe la página de vm-b mediante una dirección 10.20.1.x.

Evidencias de la práctica

FASE B · PREPARAR EL DISCO EN UBUNTU

Crea el sistema de archivos y la evidencia

  1. Abre Operaciones → Ejecutar comando → RunShellScript.
  2. Ejecuta primero lsblk y ls -l /dev/disk/azure/scsi1/. Debe aparecer lun0.
  3. Ejecuta el bloque siguiente una sola vez sobre el disco nuevo. Formatear borra lo que exista en ese disco, por eso debes verificar lun0.
UBUNTU · PREPARAR LUN 0 
DISCO=/dev/disk/azure/scsi1/lun0
printf 'n\np\n1\n\n\nw\n' | sudo fdisk "$DISCO"
sudo partx -u "$DISCO"
sudo mkfs.ext4 -F /dev/disk/azure/scsi1/lun0-part1
sudo mkdir -p /datos
sudo mount /dev/disk/azure/scsi1/lun0-part1 /datos
echo "Archivo protegido por una instantanea de Azure" | sudo tee /datos/evidencia.txt
sudo cat /datos/evidencia.txt
df -h /datos
!

Lee antes de formatear

mkfs destruye el contenido del dispositivo indicado. En esta actividad solo se autoriza sobre el disco nuevo identificado como LUN 0. Nunca lo ejecutes sobre el disco del sistema.

Congela un punto recuperable

  3. Abre Configuración → Discos y selecciona disco-datos-lab.
  4. En el disco selecciona Crear instantánea.
  5. Grupo: rg-lab-snapshot; nombre: snap-datos-lab; tipo de instantánea: Incremental si está disponible; redundancia predeterminada.
  6. Selecciona Revisar y crear → Crear.

Una instantánea incremental guarda los cambios necesarios respecto a instantáneas anteriores y se factura según datos usados. La primera todavía debe representar el contenido existente.
